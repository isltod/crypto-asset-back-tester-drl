## 2. Day 1-2: 프로토타입

### 목표
코드를 작성하고 첫 백테스트 결과를 확인하는 것. **"돌아가는 시스템"** 완성.

### 작업 내역

| 작업 | 예상 소요 | 비고 |
|------|:---------:|------|
| 바이낸스 1H OHLCV 3년치 다운로드 | 10~20분 | API Rate Limit 주의 |
| 기술적 지표 계산 모듈 | 30분~1시간 | RSI, ADX, CI, BB, ATR, MACD |
| HMM 국면 탐지 모듈 | 1~2시간 | hmmlearn 기반 |
| ADX+CI 교차검증 모듈 | 30분 | 정규화 + 결합 로직 |
| 히스테리시스 + 전환 프로토콜 | 30분 | 채터링 방지 |
| 평균회귀 엔진 | 1~2시간 | BB 기반 진입/청산 |
| 추세추종 엔진 | 1~2시간 | 돌파 + ATR 트레일링 |
| 리스크 관리 모듈 | 1시간 | 1% Risk, OCO, Kill Switch |
| 백테스터 (수수료+슬리피지 반영) | 1~2시간 | 수익률 곡선, MDD 출력 |

### ⚠️ 이 시점의 백테스트 결과를 절대 신뢰하지 말 것

첫 백테스트는 거의 100% 환상적인 수익을 보여준다. 이유:
- 파라미터가 전체 데이터에 맞춰져 있음 (과적합)
- Look-Ahead Bias가 코드에 숨어있을 확률이 높음
- 체결 가정이 비현실적 (원하는 가격에 즉시 체결)

> **이 결과는 "코드가 돌아간다"는 확인 용도로만 사용한다.**

## 3. Day 3-5: 검증 단계

### 목표
"이 성능이 진짜인가?"를 증명하거나 거짓임을 밝혀내는 것.

### 3.1 Look-Ahead Bias 검증

미래 정보가 과거 시점에 유입되는 오류. 가장 흔한 함정들:

| 함정 | 예시 | 검증 방법 |
|------|------|----------|
| 지표 계산에 현재 봉 포함 | BB(20) 계산 시 현재 종가 포함 | 지표 계산 후 1봉 shift 확인 |
| 당일 고가/저가 사전 인지 | "오늘 저점에서 샀다" | 진입 시점에 사용 가능한 데이터만 접근하는지 확인 |
| 데이터 정렬 오류 | merge/join 시 시간 어긋남 | 특정 날짜 수동 크로스체크 |

**검증 테스트:** 랜덤 시점 10개를 골라 해당 시점에서 모델이 접근 가능한 데이터를 수동으로 출력하고, 미래 데이터가 포함되지 않았는지 눈으로 확인한다.

### 3.2 Walk-Forward Optimization

과적합을 방지하는 표준 기법. 전체 데이터를 시간 순서대로 잘라서 반복 검증한다.

```
윈도우 구조 (6개월 학습 + 1개월 검증, 1개월씩 전진):

[=== 학습 6개월 ===][검증 1개월]
     [=== 학습 6개월 ===][검증 1개월]
          [=== 학습 6개월 ===][검증 1개월]
               ...반복...

총 윈도우 수: 약 24~30개 (3년 데이터 기준)
```

각 윈도우에서:
1. 학습 구간으로 파라미터 최적화
2. 검증 구간에 적용하여 Out-of-Sample 성과 기록
3. **모든 검증 구간의 성과를 이어붙인 것이 진짜 기대 성능**

### 3.3 파라미터 그리드 서치

```
탐색할 파라미터 조합:
  HMM 윈도우: [360, 540, 720, 1080, 1440]  → 5개
  히스테리시스 상한: [0.60, 0.65, 0.70, 0.75, 0.80] → 5개
  히스테리시스 하한: [0.20, 0.25, 0.30, 0.35, 0.40] → 5개
  평균회귀 손절: [-0.4, -0.5, -0.6, -0.8, -1.0]%  → 5개
  ATR 트레일링 배수: [1.5, 2.0, 2.5, 3.0]          → 4개

총 조합: 2,500개
조합당 백테스트: ~2초
연산 시간: ~1.5시간 (단일 윈도우)
× Walk-Forward 윈도우 수: 수 시간~반나절
```

## 4. Day 6-10: 안정화

### 목표
Walk-Forward에서 양수 성과를 보이는 파라미터 조합이 **다양한 극단 상황에서도 무너지지 않는지** 확인.

### 4.1 스트레스 테스트 시나리오

| 시나리오 | 테스트 방법 |
|----------|------------|
| 급락장 (2022.05 루나 사태) | 해당 구간 집중 백테스트 → Kill Switch 정상 작동 확인 |
| 급등장 (2024.01~03 ETF 랠리) | 추세 엔진이 수익을 제대로 추적하는지 확인 |
| 장기 횡보 (2023.06~09) | 평균회귀 엔진이 잔잔한 수익을 내는지 확인 |
| 변동성 폭발 (2024.08 캐리 트레이드 청산) | 포지션 사이징이 자산을 보호하는지 확인 |

### 4.2 파라미터 안정성 검증

최적 파라미터 주변을 ±10~20% 변동시켜도 성과가 크게 변하지 않는지 확인.

```
최적 손절: -0.6%
테스트: -0.5%, -0.7%에서도 양수 성과?
  → YES: 강건한 파라미터 (안정적)
  → NO:  과적합된 파라미터 (위험, 재탐색 필요)
```

**"절벽 파라미터"** (0.1% 바꾸면 성과가 급변하는 값)를 사용하면 실전에서 반드시 무너진다.

## 5. Week 3-4: 페이퍼 트레이딩

### 목표
실시간 데이터로 시스템을 가동하되, 실제 주문은 내지 않고 가상 체결로 성과를 기록.

### 확인 사항

| 항목 | 확인 내용 |
|------|----------|
| 백테스트 대비 괴리 | 실시간 성과가 백테스트와 크게 다르면 Bias 존재 의심 |
| 체결 현실성 | 진입 가격과 실제 시장 가격의 차이 (슬리피지 측정) |
| 인프라 안정성 | API 연결 끊김, 서버 다운, 데이터 지연 대응 확인 |
| 국면 전환 빈도 | 너무 잦은 전환 → 히스테리시스 조정 필요 |

## 7. 역할 분담: AI 에이전트 vs 사람

| 단계 | AI 에이전트 | 사람 |
|------|:-----------:|:----:|
| 코드 작성 | **90%** | 리뷰 및 승인 |
| 버그 수정 | **80%** | 재현 조건 제시 |
| Look-Ahead Bias 방지 구조 설계 | **70%** | 최종 수동 확인 |
| Walk-Forward 실행 자동화 | **90%** | 결과 해석 및 판단 |
| "이 구간 왜 손실인가" 분석 | 30% | **70%** (도메인 판단) |
| 파라미터 안정성 판단 | 50% | **50%** |
| 실전 투입 금액/시점 결정 | 0% | **100%** |
| Kill Switch 발동 판단 | 자동 (일일 3% 초과 시) | 수동 (거시경제 이벤트) |

## 8. 핵심 원칙 요약

1. **첫 백테스트 결과를 절대 믿지 마라** — Walk-Forward Out-of-Sample 성과만이 의미 있다.
2. **"돌아가는 코드"와 "돈을 버는 시스템"은 다르다** — 코드 완성은 전체 과정의 30%에 불과하다.
3. **절벽 파라미터를 피하라** — ±20% 변동에도 성과가 유지되는 강건한 값만 사용한다.
4. **점진적으로 신뢰를 쌓아라** — 백테스트 → Walk-Forward → 페이퍼 → 소액 실전의 순서를 뛰어넘지 않는다.
